# pi-image correctness review

Scope reviewed: `packages/pi-image-bridge/src/*`, `packages/image-tool/src/index.ts`, related tests, README, and implementation plan context. `C:\Users\Administrator\project\ts\pi-ext\plan.md` and `C:\Users\Administrator\project\ts\pi-ext\progress.md` were requested but are not present in the workspace, so this review used the checked-in plan at `docs/superpowers/plans/2026-06-16-pi-personal-tools.md` plus live source.

## Findings

### Important — Installer can report success even when autostart installation failed

- Evidence: `packages/pi-image-bridge/src/install.ts:106` creates the Windows scheduled task through `spawnSync`, but `packages/pi-image-bridge/src/install.ts:108` does not inspect `status`, `error`, or `signal`. `packages/pi-image-bridge/src/install.ts:117` similarly ignores the result of `launchctl bootstrap` on macOS. After either path, `installBridge` always reaches `packages/pi-image-bridge/src/install.ts:138` and prints that the bridge was installed.
- Why it matters: users can receive a successful install message while no login service was created, so the documented SSH paste flow fails after reboot/login with only a later bridge health failure.
- Suggested fix: check each `spawnSync` result and throw or print a clear actionable failure when service registration fails. If a fallback is available, only print success after one autostart mechanism is actually installed.

### Important — Uninstall leaves macOS and Linux autostart entries installed

- Evidence: install creates a macOS LaunchAgent at `packages/pi-image-bridge/src/install.ts:112` and bootstraps it at `packages/pi-image-bridge/src/install.ts:117`; Linux install writes a systemd user service at `packages/pi-image-bridge/src/install.ts:122` and may write an XDG autostart desktop file at `packages/pi-image-bridge/src/install.ts:129`. `uninstallBridge` only removes the SSH config block and, on Windows, deletes the scheduled task at `packages/pi-image-bridge/src/install.ts:141` through `packages/pi-image-bridge/src/install.ts:145`.
- Why it matters: after `pi-image-bridge uninstall`, Linux/macOS users can still have the bridge starting at login and exposing clipboard reads on the configured local port, contrary to the uninstall message at `packages/pi-image-bridge/src/install.ts:146`.
- Suggested fix: remove/disable the LaunchAgent, unload it if running, disable/remove the systemd user service, and remove the XDG autostart file. Report any cleanup failures explicitly.

### Important — Invalid bridge port values can produce broken SSH config and startup behavior

- Evidence: `packages/pi-image-bridge/src/cli.ts:8` passes `Number(process.env.PI_IMAGE_BRIDGE_PORT || "38991")` directly to `serveBridge`. `packages/pi-image-bridge/src/install.ts:91` uses the same unchecked conversion for the SSH `RemoteForward` port, and `buildSshConfigBlock` writes it into the config at `packages/pi-image-bridge/src/install.ts:15`. `verifyManagedSshConfig` only checks for that same computed string at `packages/pi-image-bridge/src/install.ts:60`, so `PI_IMAGE_BRIDGE_PORT=abc` would verify a `RemoteForward 127.0.0.1:NaN 127.0.0.1:NaN` block instead of failing.
- Why it matters: a mistyped environment variable can silently corrupt the managed SSH config or make the server fail to start with a low-level runtime error.
- Suggested fix: centralize port parsing and require an integer in `1..65535`; reject invalid values before writing SSH config or calling `server.listen`. If `--port` is intended as an advanced installer flag, parse and validate it consistently too.

### Important — Forwarded clipboard endpoint has no authentication or install-time security notice

- Evidence: `packages/pi-image-bridge/src/server.ts:19` through `packages/pi-image-bridge/src/server.ts:31` returns the current clipboard image to any request for `/clipboard-image`. The default managed SSH config generated by `packages/pi-image-bridge/src/install.ts:10` through `packages/pi-image-bridge/src/install.ts:15` applies to `Host *` unless restricted. The success message at `packages/pi-image-bridge/src/install.ts:138` does not warn that processes on a connected remote host can request the current local clipboard image. The implementation plan explicitly called for this notice at `docs/superpowers/plans/2026-06-16-pi-personal-tools.md:20`.
- Why it matters: the default no-touch SSH flow intentionally forwards the local clipboard bridge to remote loopback, but without a warning users may not realize any process on that remote host during the SSH session can fetch clipboard images.
- Suggested fix: print a concise one-time install notice describing the remote-loopback exposure and host restriction options. Prefer adding an opt-in token/header shared through the SSH config or Pi settings if it can preserve the no-touch flow.

### Important — `generate_image` accepts multiple-image requests but only saves one result

- Evidence: `packages/image-tool/src/index.ts:12` and `packages/image-tool/src/index.ts:28` include `n` in the supported request shape, and execution forwards `params.n` to the API at `packages/image-tool/src/index.ts:333`. Response extraction returns the first payload found in arrays at `packages/image-tool/src/index.ts:95` through `packages/image-tool/src/index.ts:99`, and execution writes a single `output` file at `packages/image-tool/src/index.ts:356` through `packages/image-tool/src/index.ts:361`.
- Why it matters: a user or agent can request `n > 1`, potentially paying for multiple generated images, while the tool silently persists only the first image and discards the rest.
- Suggested fix: either reject `n > 1` with a clear error until multi-output saving is implemented, or add deterministic output naming and return all saved paths.

### Minor — Bridge startup errors are not converted into actionable diagnostics

- Evidence: `createBridgeServer` awaits only the `listen` callback at `packages/pi-image-bridge/src/server.ts:37`; it does not attach a one-time `error` listener that rejects the promise. `serveBridge` at `packages/pi-image-bridge/src/server.ts:46` through `packages/pi-image-bridge/src/server.ts:48` therefore does not provide a controlled error path for common startup failures such as `EADDRINUSE` or invalid bind addresses.
- Why it matters: users troubleshooting port conflicts can get an uncaught Node error or a hung startup instead of a clear message telling them which port/host failed and how to change it.
- Suggested fix: wrap `server.listen` with both `listening` and `error` handling, reject with a friendly error, and have the CLI print it with a non-zero exit code.

### Minor — Linux clipboard reader only requests PNG data

- Evidence: on Linux, `readClipboardImage` requests `image/png` from `wl-paste` at `packages/pi-image-bridge/src/clipboard.ts:36` and from `xclip` at `packages/pi-image-bridge/src/clipboard.ts:38`; it does not try other common clipboard image MIME types such as `image/jpeg` or `image/webp` before falling back.
- Why it matters: the user-facing flow says it pastes a local clipboard image, but JPEG/WebP clipboard contents may be reported as missing depending on the clipboard provider instead of being pasted.
- Suggested fix: probe available image MIME types or try a short ordered list (`image/png`, `image/jpeg`, `image/webp`) and return the matching MIME type with the bytes.
